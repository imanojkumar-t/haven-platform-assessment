B1 — The Glacier cost gotcha
Short answer

Deleting on day 40 doesn't save the money the archive rule was supposed to save. Glacier Flexible Retrieval (GLACIER) has a 90-day minimum storage duration. An object deleted 10 days after transition is billed as if it had stayed the full 90 days (an "early deletion" charge for the remaining 80 days). On top of that, the transition itself costs a per-object request fee. For a photo deleted at day 40, the Glacier rule is more expensive than leaving it in Standard.

The fix is to stop using a storage class with a minimum duration for data whose lifetime is unpredictable. I'd keep photos in Standard for the first 30 days, then move them to S3 Intelligent-Tiering, which has no minimum storage duration and no early-delete charge.

What the current rule actually costs

Illustrative us-east-1 list prices (plug in your region's numbers; the shape of the result doesn't change):

S3 Standard: ~$0.023 / GB-month
Glacier Flexible Retrieval: ~$0.0036 / GB-month, 90-day minimum
Lifecycle transition to Glacier: ~$0.03 per 1,000 objects
Assumed average photo: 2 MB, so ~512 objects per GB

Cost per GB for a photo uploaded day 0, archived day 30, deleted day 40:

Component	Cost / GB
Standard, days 0–30	$0.0230
Glacier, days 30–40 (10 days actually stored)	$0.0012
Early-deletion charge (remaining 80 days of the 90-day minimum)	$0.0096
Transition request fee (512 objects × $0.03 / 1,000)	$0.0154
Total with the Glacier rule	≈ $0.0492
Total with no archive rule (40 days in Standard)	≈ $0.0307

The rule costs about 60% more than doing nothing for this object. Two things make it worse than it looks:

The transition request fee is often the bigger hit for small objects. Glacier also adds ~40 KB of per-object metadata overhead (32 KB billed at Glacier rates, 8 KB at Standard rates), which hurts thumbnails badly.
It's invisible to the budget. The forecast assumes "sold photos cost ~$0.0036/GB-month from day 30." The early-deletion charge shows up under the usage type EarlyDelete-ByteHrs (Cost Explorer / CUR), which nobody is watching.

Deleting immediately is still the right call for compliance. Waiting doesn't avoid the charge, because the 90 days are owed either way. The money is lost at transition time, not at deletion time.

Break-even for Glacier
archive cost  = 0.0230 + 0.0108 (90-day Glacier min) + 0.0154 (transition) = 0.0492   (flat until ~day 120)
standard cost = 0.023 × (days / 30)
break-even    ≈ day 64   (≈ day 44 if you ignore the transition fee)

Anything deleted before roughly day 64 loses money under this rule.

Other problems in the original rule
No filter. The rule is named archive-sold-listing-photos but applies to every object in haven-listing-media: active listings, thumbnails, everything.
Versioning. If versioning is (or ever gets) enabled, a "delete" only adds a delete marker. The photo still exists as a noncurrent version, is still billed, and doesn't meet the deletion requirement.
days = 30 counts from upload, not from sale. Lifecycle rules can't count from when a tag was applied.
Small objects. Objects under 128 KB are better left alone: per-object fees and overhead exceed the savings.
Redesign: Standard for 30 days, then Intelligent-Tiering
How Intelligent-Tiering behaves
Objects enter the Frequent Access tier (same price as Standard).
After 30 days with no access they move to Infrequent Access (~$0.0125/GB-month).
After 90 days with no access they move to Archive Instant Access (~$0.004/GB-month), still millisecond retrieval.
Any access moves the object back to Frequent.
There is a monitoring fee of ~$0.0025 per 1,000 objects per month. Objects under 128 KB aren't monitored or tiered.
No minimum storage duration, so deleting at any age never triggers an early-delete charge.
Cost for the day-40 deletion case (per GB)
Approach	Cost / GB
No rule (Standard to day 40)	~$0.031
Upload directly as Intelligent-Tiering	~$0.029
Standard to day 30, then Intelligent-Tiering	~$0.036
Original Glacier rule	~$0.049

The Standard-first path includes a transition fee of ~$0.01 per 1,000 objects (~$0.005/GB) and a short stretch of monitoring. It's slightly worse than doing nothing for objects deleted right after the transition, but removes the large early-delete penalty and the Glacier transition fee.

Why Standard-first rather than direct upload

Uploading with StorageClass=INTELLIGENT_TIERING is cheaper per object (no transition fee, and the Infrequent tier is reached at day 30 instead of day 60). Standard-first is the better choice when:

You have existing objects already in Standard.
A large share of deletions happen in the first 30 days, so those objects never pay transition or monitoring fees.
You want storage class managed only through lifecycle rules, with no application change.

Payback: once an object reaches the Infrequent tier it saves ~$0.009/GB-month after monitoring. That recoups the transition and monitoring costs within a few weeks, so Standard-first beats staying in Standard for anything that lives past roughly day 80.

Long-term trade-off versus Glacier

Long-lived photos settle at about $0.004 + ~$0.0013 monitoring ≈ $0.005/GB-month in Archive Instant Access, versus ~$0.0036 for Glacier. That premium buys immunity from deletion-timing penalties and instant retrieval instead of Glacier's retrieval delay. If nearly all photos live for years and deletions are rare, Glacier at a later cutoff can win in steady state. With unpredictable deletion timing, Intelligent-Tiering is the safer choice.

Terraform
hcl
resource "aws_s3_bucket_lifecycle_configuration" "listing_media_archive" {
  bucket = aws_s3_bucket.listing_media.id

  # Explicit rather than relying on the AWS default: skip transitions for objects < 128 KB.
  transition_default_minimum_object_size = "all_storage_classes_128K"

  # Standard for 30 days, then Intelligent-Tiering (no minimum duration, no early-delete charge).
  rule {
    id     = "sold-listing-photos-to-intelligent-tiering"
    status = "Enabled"

    filter {
      and {
        prefix                   = "photos/"                     # thumbnails live elsewhere and stay in Standard
        tags                     = { listing_status = "sold" }   # app sets this tag when the listing sells
        object_size_greater_than = 131072
      }
    }

    transition {
      days          = 30   # tune from real deletion-request age data
      storage_class = "INTELLIGENT_TIERING"
    }
  }

  # Only needed if versioning is enabled, so "delete" really removes data within the 30-day SLA.
  rule {
    id     = "expire-noncurrent-versions"
    status = "Enabled"

    filter {}

    noncurrent_version_expiration {
      noncurrent_days = 1
    }
  }

  # Housekeeping: stop paying for abandoned multipart uploads.
  rule {
    id     = "abort-incomplete-multipart"
    status = "Enabled"

    filter {}

    abort_incomplete_multipart_upload {
      days_after_initiation = 7
    }
  }
}

Notes:

The app must apply listing_status=sold when a listing sells, or nothing transitions. Drop the tag filter if you'd rather transition every photo under photos/; active listings' photos stay in the Frequent tier while viewed, but you'd pay the transition fee on them for little benefit.
Pick the days value from data: pull deletion-request ages from application logs and set it past the point where most requests have already happened.
If versioning is off, remove the noncurrent-version rule.
Guardrails so this can't quietly drift again
Alert (AWS Budgets / Cost Anomaly Detection) on lifecycle transition request counts and on the EarlyDelete-ByteHrs usage type. It should stay at zero under this design.
Track Intelligent-Tiering monitoring cost per month; it grows with object count, not bytes.
Review actual average object size with S3 Storage Lens. The 2 MB assumption drives the transition and monitoring estimates.
Assumptions to verify
Prices above are approximate us-east-1 list prices; check your region and any enterprise discounts.
Whether bucket versioning is enabled isn't visible in the Terraform shown, and it changes the deletion story significantly.
